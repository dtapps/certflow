# ADR-0005：非数据库 ID 统一用 UUID v7

- 状态：已采纳
- 日期：2026-07 起沿用（随项目建立）
- 相关：[database.md](../database.md)、[architecture.md](../architecture.md)

## 背景

应用里有几类 ID 不属于业务主键：

- gocron 的任务标识（`gocron.WithIdentifier(func() uuid.UUID)`）；
- 系统桌面通知的标识（每次发送生成一个，交给系统通知服务）；
- 调用云厂商 API 时需要的请求 ID（如天翼云 `requestID`）。

这些 ID 的要求：

- 不能重复（跨进程、跨重启都不该撞）；
- 尽量有序，便于日志排序与调试；
- 生成成本低，不依赖数据库自增；
- 不暴露业务语义（不要用「时间戳 + 自增」拼字符串）。

业务表主键则保持 ent 默认的自增 `int`：SQLite 下简单、索引小、与 ent 的关联查询契合。

## 决定

**凡是需要「非数据库主键」的全局唯一 ID，一律用 UUID v7**：

```go
id, err := uuid.NewV7()
```

- 使用 `github.com/google/uuid`（`go.mod` 锁定 v1.6.0），不是标准库（标准库的 UUID 支持要 Go 1.27+，项目暂不依赖）。
- 业务表主键不改，仍是 `int` 自增。
- 需要字符串时用 `.String()`；gocron 需要 `uuid.UUID` 时直接传。

## 为什么是 v7

- **时间有序**：v7 的高位是毫秒时间戳，生成顺序与时间顺序一致，写日志、排序、排查都比 v4 友好（v4 完全随机）。
- **唯一性不依赖中心**：不需要数据库序列或额外协调。
- **不泄露太多信息**：只暴露毫秒级时间，不像「自增 ID」那样暴露业务量。
- **生态支持**：`google/uuid` 的 `NewV7()` 返回 `(UUID, error)`，错误只在随机源失败时出现。

## 后果

正面：

- 任务 ID、系统通知 ID、请求 ID 互不冲突，格式统一、便于日志串联。
- 不引入数据库依赖，测试里也能直接生成。
- 与 ent 的自增主键分工明确：内部关联用 int，外部 / 临时标识用 UUID。

负面 / 注意：

- `NewV7()` 返回两个值，调用处必须处理 error（gocron 的 `WithIdentifier` 里用 `id, _ :=` 忽略，因为失败概率极低且没有可用的降级路径）。
- UUID 字符串比自增数字长，不适合当高频查询的索引键；这也是业务表主键不换 UUID 的原因。
- 需要解析外部传入的 job ID 时（`Scheduler.GetJob`）要处理非法格式，返回错误而不是 panic。

## 备选方案

- **UUID v4**：唯一性够，但无序，日志里难排；没有时间信息。
- **自增整数**：简单，但跨进程 / 跨设备不唯一，且暴露业务量。
- **ULID / KSUID**：同样时间有序，但生态与团队熟悉度不如 `google/uuid`；项目规则已明确 v7。

## 证据

- `internal/scheduler/service.go`：`gocron.WithIdentifier` 用 `uuid.NewV7()`
- `internal/notification/service.go`：通知 ID 用 `uuid.NewV7()`
- `internal/deploy/ctyun.go`：请求 ID 用 `uuid.NewV7().String()`
- `go.mod`：`github.com/google/uuid v1.6.0`
- `AGENTS.md`：UUID 规则（必须 v7，必须用 `github.com/google/uuid`）
