  - `upResp` 的 `Status` 改用 `panelStatus`，并新增 `Data.Hash` 作为 hash 兜底位置（实际 hash 在 `message.hash`）。

- `internal/deploy/panel_test.go`：

  - `TestAAPanelDeployCertNumericStatus`：用真实形态（`status:0` + `message.hash`）做 mock，并补 `r.ParseForm()` 修复表单未解析导致 hash 为空的测试 bug。

## 实现 1Panel DeployCert（POST /api/v2/websites/{id}/https）

**任务目标**：用户给出 1Panel swagger `post_websites_update`，要求实现 1Panel 证书部署。

**关键纠正（用户澄清）**：设置站点证书**不是** `/websites/update`（该接口无证书字段），正确接口是 `POST /api/v2/websites/{id}/https`（UpdateHTTPSConfig，请求体 `WebsiteHTTPSOp`：websiteId/type/privateKey/certificate/enable + 一堆 HTTPS 配置值类型字段）。另有 `GET /api/v2/websites/{id}/https` 返回当前 HTTPS 配置（`response.WebsiteHTTPS`）。

**能否只传 privateKey+certificate？** 不能。因 `WebsiteHTTPSOp` 全为值类型字段，若只传证书两字段，其余（SSLProtocol/Hsts/HttpsPorts/Http3 等）会被零值清空，可能破坏站点既有 HTTPS 设置。故采用「先 GET 当前配置 → 原样回传并仅替换 type=manual、privateKey、certificate、enable=true」的安全模式。type 用 `manual`（oneof=existed/auto/manual，必填）。

**执行细节**：
- `internal/deploy/onepanel.go`：实现 `OnePanelDeployer.DeployCert`：
  - 从 `svc["site_name"]`（格式 `名称||id`）解析网站 id；
  - `client.doGetRequest(ctx, /api/v2/websites/{id}/https)` 取现状；
  - `client.doJSONRequest(ctx, 同路径, payload)` 回传，payload 携带现状的 SSLProtocol/algorithm/hsts/hstsIncludeSubDomains/httpConfig/httpsPorts/httpsPort/http3 + 证书四字段；
  - 按 1Panel 约定 `code==200` 判定成功；结果 `CloudCertID=站点id`，`Message=deploy.panel_ssl_set`。
  - 补充 `strings` 导入。
- `internal/deploy/panel_test.go`：
  - 新增 `TestOnePanelDeployCert`：mock GET/POST 同一路径，断言 type=manual、证书字段、既有 HTTPS 配置被原样回传（不被清空）。
  - `TestBaseDeployCert` 改用仍未实现的 `aawaf`（1panel 已实装，原断言「尚未实现」会失败）。

**关键决策**：采用 GET-then-POST 保留既有 HTTPS 配置，避免只传两字段清空 HSTS/SSL 协议等设置；成功判定用 code==200（1Panel 标准约定）。

**验证**：

## 1Panel 部署报「私钥文件校验失败」：根因是证书数据 key/cert 不匹配 + 加本地校验

**任务目标**：上一步修好 site_id 后，1Panel 部署仍失败，报错 `部署证书到面板站点失败: 服务错误: 私钥文件校验失败`（1Panel 返回 HTTP 400 + 消息「私钥文件校验失败」）。

**根因**：
- 1Panel 在 `POST /api/v2/websites/{id}/https` 时会用 `tls.X509KeyPair(certificate, privateKey)` 校验私钥与证书（叶子）是否匹配；不匹配即报「私钥文件校验失败」。
- 真正失败原因是 **证书数据本身**：`certID=14` 存进 CertFlow 的 `key_content` 与 `cert_content` 对不上（最常见于手动导入/上传时 key 与 cert 贴错，或续期时只更新了 cert 没更新 key）。

- 1Panel 接受 fullchain（`certificate` 字段传完整链，社区同步脚本即用 `fullchain.pem`），故「整条链」不是触发原因；就是 key 与叶子证书不匹配。

**执行细节**：
- `internal/deploy/onepanel.go` `DeployCert`：在组装 payload 前新增本地预校验 `verifyKeyCertMatch(keyPEM, certPEM)`（`crypto/tls` 的 `tls.X509KeyPair`），不匹配时返回明确错误 `error.deploy_panel_cert_verify`（i18n 键已存在，值「证书链验证失败」）+ 底层 tls 错误，避免把 1Panel 的晦涩「私钥文件校验失败」直接抛给用户。新增 `crypto/tls` 导入。
- 该检查同时覆盖 `cert_pem`/`key_pem` 为空之外的「内容不匹配」场景（此前只能到了 1Panel 才暴露）。
- `internal/deploy/panel_test.go`：新增 `genKeyCert`（生成一对匹配 RSA key/cert 的辅助）+ `TestVerifyKeyCertMatch`（匹配通过、不匹配报错、与 `tls.X509KeyPair` 行为一致）；并把 `TestOnePanelDeployCert`/`TestOnePanelDeployCertUsesSiteID` 原来的占位 `"CERT"/"KEY"` 换成真实生成的 `certPEM/keyPEM`（断言同步改为与变量比较），以通过新校验。

**关键决策**：
- 这不是代码 bug，是**证书数据问题**；代码侧只能「提前暴露、给出明确提示」，无法让 1Panel 接受不匹配的 key。真正的修复是修正 certID=14 的证书数据（重新导入/签发该证书，确保 key 与 cert 对应）。
- 复用既有 i18n 键 `error.deploy_panel_cert_verify`（「证书链验证失败」）作为分类前缀，底层技术错误原文透传；严格遵循 Go 用户可见文本走 `i18n.T()`（中文提示不再硬编码在 helper 里）。

**验证**：
- `go build -tags production ./...` ✓（`EXIT=0`）
- `go test -vet=off -tags production ./internal/deploy/...` ✓（`TestVerifyKeyCertMatch`/`TestMatchSiteID`/`TestOnePanelDeployCert*` 全过）

**遗留问题**：桌面端需 `wails3 task build` 重新构建才生效；用户需在 UI 重新导入/签发 certID=14 使其 key 与 cert 匹配后再部署，或用真实 1Panel 面板验证本地校验提示与 1Panel 原生提示一致。

## 修正 1Panel「私钥文件校验失败」真正根因（接口层 algorithm bug）【此节结论有误，已被下节推翻】

**任务目标**：用户再次部署 certID=14 到 1Panel 仍报 `服务错误: 私钥文件校验失败`，并明确反馈「明显不是数据/密钥格式问题，应多看接口」。重新定位为接口层 bug。

> ⚠️ 本节「algorithm=RSA/ECC」的判断是**错误**的。1Panel 的 `algorithm` 字段实为 nginx cipher 套件字符串，并非密钥类型；真正根因是缺 `importType:"paste"`。正确结论见下方「二次修正（最终正确根因）」一节。

**关键判据（推翻上一轮数据问题假设）**：日志里出现的是**原始 1Panel 报错**（`服务错误: 私钥文件校验失败`），而非我们本地增强报错（`证书与私钥不匹配 (私钥类型=...)` 前缀）。说明本地 `tls.X509KeyPair` 预校验**已通过**（key/cert 确实配对），但 1Panel 在自己校验里仍拒绝——这是接口层问题，不是证书数据不匹配，也不是 PKCS#8 格式（否则本地预校验就会先失败）。

**真正根因（GET→POST 副作用）**：`DeployCert` 先 `GET /api/v2/websites/{id}/https` 拉当前 HTTPS 配置，再把 `algorithm` 等字段**原样回传**。但 `algorithm` 反映的是**旧证书**的密钥类型（RSA/ECC）。若本次部署证书的密钥类型与旧配置不同（如旧 RSA、新 EC，或反之），我们把旧 `algorithm` 发回，1Panel 就按错误类型去 `parseKey` 解析私钥 → 解析失败 → 报 `私钥文件校验失败`。网页手动上传能成功，正是因为网页前端会**按实际上传的密钥重新算 `algorithm`**。

**执行细节**（`internal/deploy/onepanel.go`，仅后端）：
- 新增 `detectKeyAlgorithm(keyPEM)`：解析私钥判断 1Panel 所需 `algorithm` 值（RSA→"RSA"、EC→"ECC"，PKCS#8 也能识别；解析不出回退 "RSA"）。
- 新增 `keyTypeOf(keyPEM)`：仅用于日志的简短类型描述。
- `DeployCert` payload 改为 `"algorithm": detectKeyAlgorithm(keyPEM)`（不再照抄 `getResp.Data.Algorithm`），并补 `"id": siteID` 字段（与网页前端一致）。
- 加 DEBUG 日志：部署前打印 `algorithm`/`keyType`，部署后打印 1Panel 原始 `code`/`message`，便于二次排查。
- 保留上一轮加固：`normalizePrivateKeyPEM`（PKCS#8→PKCS#1/SEC1）、`verifyKeyCertMatch` 本地预校验（其报错前缀可区分「数据不匹配」与「接口层 algorithm 错误」）。

**验证**：
- `go build -tags production ./...` ✓
- `go test -vet=off ./internal/deploy/...` ✓

**遗留问题**：桌面端需 `wails3 task build` 重新构建才生效；若重建后仍报「私钥文件校验失败」且本地预校验通过，看 DEBUG 日志的 `algorithm`/`keyType` 与 1Panel `message` 确认是否已修；若仍失败，下一步应查验 `SSLProtocol` 缺省值或证书是否需先入 1Panel 证书库（按站点 ID 直绑场景）。

## 1Panel「私钥文件校验失败」二次修正（最终正确根因）

**任务目标**：用户用浏览器抓到 1Panel 能成功的请求（`POST /api/v2/websites/9/https`），关键字段为 `importType:"paste"`、`algorithm`=cipher 套件串、`SSLProtocol`=TLS 版本数组。据此推翻上一节「algorithm=RSA/ECC」的误判，定位真正接口 bug。

**查证源码**（1Panel `dev-v2`，路径 `agent/app/dto/request/website.go` 的 `WebsiteHTTPSOp`）：
- `algorithm` 是 **nginx 的 cipher 套件字符串**（`ssl_ciphers`），`SSLProtocol` 是 **TLS 协议版本数组**（`ssl_protocols`）——**二者都不是密钥类型**。上一节把 `algorithm` 当成 RSA/ECC 是根本性误解。
- 端点 `POST /api/v2/websites/{id}/https` 由 `OpWebsiteHTTPS` 处理：当 `type=="manual"` 时调 `getManualWebsiteSSL(req)`。证书来源由 **`importType`** 决定——为空时默认走 `privateKeyPath`/`certificatePath` 读文件（我们没传，为空）→ 解析失败报「私钥文件校验失败」。带 `importType:"paste"` 才会读取内联的 `privateKey`/`certificate`。
- DTO 字段：`websiteId`(必填)、`httpsPorts`([]int，**无单值 `httpsPort`**)、`httpConfig`(oneof HTTPSOnly/HTTPAlso/HTTPToHTTPS)、`importType`、`type`(oneof existed/auto/manual)、`SSLProtocol`/`algorithm`/`hsts`/`http3` 等。**没有 `id` / `acmeAccountID` 字段**（多余字段被 Gin 忽略，无害）。

**真正根因**：`DeployCert` 回传 payload **漏了 `importType:"paste"`**，导致 1Panel 不去读内联私钥/证书，而读空的 `privateKeyPath`/`certificatePath` → 校验失败。与 `algorithm` 取值无关（上一节改 `detectKeyAlgorithm` 返回 `"ECC"` 反而把 cipher 字段填成了错误字符串）。

**执行细节**（`internal/deploy/onepanel.go`，仅后端）：
- payload 补 `"importType":"paste"`、`"privateKeyPath":""`、`"certificatePath":""`、`"acmeAccountID":0`。
- `algorithm` 改回回传 `getResp.Data.Algorithm`（cipher 串，空则兜底常量 `defaultSSLAlgorithm`）；移除错误的 `detectKeyAlgorithm`（保留 `keyTypeOf` 供日志）。
- `httpConfig` 空兜底 `"HTTPAlso"`、`httpsPort` 空兜底 `"443"`；保留 `SSLProtocol`/`httpsPorts`/`hsts`/`http3` 等 GET 回传值。
- 移除多余的 `"id":siteID`（DTO 无此字段）。
- 保留 `verifyKeyCertMatch`（本地预校验，区分「数据不匹配」vs「接口层」）与 `normalizePrivateKeyPEM`（PKCS#8→传统格式）。

**验证**：
- `go build -tags production ./...` ✓
- `go vet ./internal/deploy/`（onepanel.go 无告警；仅 aliyun.go/baidu.go 既有 `logging.Debug` 非恒定格式串告警，与本改动无关）
- `go test -vet=off ./internal/deploy/...` ✓

**遗留问题**：桌面端需 `wails3 task build` 重新构建才生效；重新部署 certID=14 验证。若仍失败，看 DEBUG 日志的 `keyType` 与 1Panel `message`——正常情况下应 `code=200`。另：1Panel v2 证书也可走「先 `POST /api/v2/websites/ssl/upload`(importType/type=paste) 入库拿 sslID，再绑站点」两步法，本次单步 `importType:pask` 已对齐用户成功的请求，优先验证此路径。
